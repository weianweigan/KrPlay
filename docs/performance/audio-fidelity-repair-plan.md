# CarPlay 音频连续性与保真修复方案

状态：实现与实机复测中。2026-10-28。

用户最新约束：音乐缓冲由客户端独立设置，默认 300 ms，提供 500/1000 ms。服务端本地音频设置保持用于服务端播放，不作为客户端配置来源。下文早期规划的 800–1000 ms 是实车实验建议，不覆盖客户端默认值。

## 目标与依据

默认优先保留音乐样本、声道和动态范围，在可控延迟内连续播放。通话、Siri、导航使用独立低延迟策略。旧任务中“600 ms 抖动后直接丢弃过期 PCM”的要求需要收窄到确实无法及时播放的交互音频或明确的流重置，不能用统一 120 ms 门槛裁剪音乐。

实测依据：logs/device-performance-20261028/REPORT.md。用户确认三星持续断音，161.528 秒日志内新增 4543 个 PCM 丢弃计数，AudioTrack 有欠载；音乐上游收包间隔反复达到 390–405 ms，最大约 750 ms。独立 Wi-Fi 五轮 RTT P95 4.896–7.364 ms、下行 190.82–246.01 Mbps。未证明全部间隔来自网络，也未证明 8295 的 QNX 调度是本次三星问题的原因。

代码证据：AndroidMediaSink.AudioRenderer.writePcm 在远端转发成功后跳过本地 MediaAudioBuffer 的预缓冲/重缓冲；ClientAudioRoute 拆成 <=20 ms PCM 块后立即发送，没有时间节奏；两端 RealtimeAudioQueue 共用 120 ms 容量/年龄阈值，客户端丢弃后 flushTracks 会清空已提交播放的样本。

## 已确认：现有 1000 ms 设置未贯通远端播放

测试会话日志在 10:02:34、10:04:08 等时间明确记录 `bufferMs=1200 startMs=1000`：配置已被服务端读取，用于创建服务端本地 AudioTrack（1000 ms 启动门槛加 200 ms 容量余量）。但当前输出为 CLIENT，`writePcm` 在 `remoteOutput` 成功后暂停/清空本地 Track 并提前返回，该 Track 的预缓冲不参与三星播放。远端协议没有传递此设置；三星 ClientAudio 仍请求至少 40 ms 的硬件缓冲（受系统最小值影响），软件队列仍为 120 ms，创建 Track 后立即 play。

因此现有设置保存和本地配置有效，但对当前客户端输出没有提供 1000 ms 音乐储备。按用户后续要求，修复改为由客户端保存音乐缓冲设置（默认 300 ms），在音频协议握手时告知服务端以设置发送窗口，并展示“设置值 / 实际预缓冲 / 待播放储备”。服务端的 1000 ms 设置不会自动覆盖客户端。

## 保真边界

- 保持 iPhone 实际协商并解码得到的采样率、声道与有效精度，不增加一次有损编码，不默认降采样、改单声道、压缩动态或增加响度处理。
- 本次输入为 AAC-LC；现有 RemoteAudioRoute/AudioWire 为 PCM16。目标是转发段不再额外损伤解码后的音频，不能称源音频“无损”或凭空恢复 24-bit 信息。
- 正常连续音乐不插入淡入淡出、不删样本、不靠持续加速追赶。淡变只用于真正的启停、切流或无法避免的断续边界，并记录处理过的样本。
- 对更高位深源先审计实际解码输出，再扩展格式协商；不以填充低位或升采样冒充高解析度。
- Android/车机混音器、输出路由、DSP 可能重采样或处理声音。PCM 传输段可做逐样本一致性验证，扬声器端不能承诺 bit-perfect。

## 设计

### 1. 传递流语义与时间线

设计 AudioWire v2 协商：流 ID/代次、用途（音乐、通话、Siri、导航）、采样率、声道布局、PCM 格式、递增序号、首样本索引、帧数、明确的 START/END/ABORT/FORMAT_CHANGE。可携带源 PTS 与源时钟频率，不能把 RTP 时钟直接当 PCM 采样时钟；Opus 存在两者不同的情况。

客户端回传实际播放进度、队列可用容量和欠载信息，用于服务端限流和诊断。序号/样本索引用于发现缺口与重复，绝不以本地收包时间替代真实媒体时间。跨端时间估计单独带误差范围。

协议显式协商版本，支持旧端但报告旧模式能力；不能向 v1 解析器直接追加字段。v1 缺少用途与时间线，不能猜测所有 type 均为音乐，完整质量验收要求两端更新。

### 2. 让音乐缓冲承受实际突发

音乐采用按 PCM 帧数计量的有界队列，容量、目标水位、真实过期条件分别建模。删除“到达后 120 ms 就过期”的音乐规则。按流隔离队列，不允许音乐挤掉导航、通话或停止事件。

第一轮 A/B 候选参数（均为实验值）：

| 配置 | 音乐启动储备 | 端侧总缓存容量 |
|---|---:|---:|
| 普通设备对照 | 500 ms | 1000 ms |
| 8295 抗抖动候选 | 800–1000 ms | 1500 ms |

这些是客户端软件队列与已提交 AudioTrack 的合计预算，不是每层各加一份。48 kHz 双声道 PCM16 的 1500 ms 约为 288 kB，内存不是主要矛盾；主要代价是启动、切歌和交互延迟。

根据实际可播放储备、欠载、到包间隔和写入停顿调整目标，而非依据控制 RTT P95 直接推断音频预算。网络恢复后允许有界突发补足储备；不要用严格 1x 发送速度阻止补库。仅对高于目标水位的数据按客户端播放进度节奏发送，避免无界灌入 TCP。

音乐不因日常队列水位上涨而丢弃。触及硬上限时先反馈限流；服务端保持有界队列且不阻塞视频或控制线程。若长期源/输出速率不匹配或不可背压，显式报告并受控重缓冲/重同步，记录损失，不能承诺无限保留。

正常结束排空尾音；用户停止、切歌、通话抢占用独立的取消语义及时丢弃旧代次。不要将新曲、旧曲或不同用途音频拼接播放。

### 3. 客户端播放状态机

音乐：等待配置 → 预缓冲 → 播放 → 欠载重缓冲 → 播放/排空结束。

- 网络线程只接收和入队，播放线程单独驱动 AudioTrack，使用音频线程优先级但不假设能绕过 QNX 调度。
- 音乐不强制使用最小低延迟缓冲。检查实际授予容量，预缓冲门槛不得超过可写容量，避免暂停状态写满后死锁。
- 根据 playbackHeadPosition/AudioTimestamp 与已写帧数跟踪实际消耗；处理回绕、轨道重建及路由切换。写入成功字节数不能标成“已经播放”。
- 短时欠载保留未播放样本，暂停并重缓冲；不因任意队列淘汰就 flush 全部 Track。只有明确代次改变或不可恢复错误才清空相关流。
- 短提示音和曲尾必须能在小于启动门槛时完成播放，不能永久卡在预缓冲。
- 通话、Siri、导航分别映射 AudioAttributes/焦点与抢占规则；按输入格式保真传输，按用途设置更小储备。具体延迟预算以回声、对话和导航实测定标，不继承音乐的 800–1000 ms。
- 音频重连只影响音频；重连必须恢复流配置与代次，禁止重播旧缓冲或触发视频重置。

### 4. 时钟漂移和虚拟机限制

先用 30–60 分钟日志验证源帧计数与真实播放进度的长期差值。优先利用可用源流控和媒体时钟，避免固定时钟累积漂移。若必须异步采样率转换，应作为明确的后续设计：高质量、平滑且有界、测量频响/失真，并披露不再逐样本恒等。不能用定期删块或改播放速率掩盖漂移。

网络停止/应用线程暂挂时，已经提交且仍被宿主音频服务消费的储备才可能继续响；仅存在 Java 队列里的样本不能保证覆盖整个 VM 暂停。若宿主同时暂停媒体服务或 VPU/音频后端，应用层不能保证无断音。实车要分别验证网络暂停、播放线程暂停、整个 VM/宿主资源争用，不能把三者混为一种故障。

音乐增加缓冲不应让 CarPlay 触控/地图整体延后。导航与通话独立低延迟；如有需严格音画同步的媒体场景，应按同一时间线另行验收，不能假设增大音乐缓存仍天然同步。

## 实施顺序

1. 补测量：记录服务端解码输出/发送、客户端接收/入队/写入/实际播放帧数；队列以毫秒和帧数展示，区分容量淘汰、真实超时、主动停止、欠载、重缓冲、flush、连接代次。修正本地 playing=false/underruns=0 被误读为远端无故障的问题。
2. 实现 v2 流语义、每流队列和音乐预缓冲；两端同时删除音乐 120 ms 淘汰策略。保留可选实验配置和版本回退路径。
3. 实现播放状态机、尾音/取消语义、消费反馈和有界发送，确保控制与视频不被音频等待阻塞。
4. 在当前 vivo + 三星做相同曲目/音量/路由 A/B；通过后再上 8295。长期漂移和更高位深扩展在连续性修复验证后单独推进。

涉及主要文件：AudioWire.java、RealtimeAudioQueue.java（拆分或参数化用途策略）、RemoteAudioRoute.kt、ClientAudioRoute.kt、AndroidMediaSink.kt、MediaAudioBuffer.kt、ClientAudio.java、MainActivity.java，以及对应协议/播放测试。

## 验收

- 确定性回放：按本次实际批量节奏注入音频；100/300/600/750 ms 停顿与恢复突发、背压、短尾音、停止/切歌、格式改变、重连；检查帧序、代次、边界、缓冲有界及音视频隔离。
- 保真：已知 PCM 的转发输出逐样本一致（排除明示边界淡变），声道不串换，帧数无缺失/重复；静音、低电平、满幅、左右独立信号检查截幅与噪声。录音或回环只在实际声学测量阶段使用。
- 普通设备音乐连续播放至少 30 分钟；用户无断音/爆音，应用正常播放段丢样本与 flush 均为 0，启动稳定后 AudioTrack 欠载增量为 0。失败必须报告，不以平均吞吐或字节增长代替听感验收。
- 在已建立且剩余可播放储备大于停顿加调度余量的条件下，600 ms 网络暂停应不丢样本、不欠载；更长或连续停顿允许明确重缓冲，不能宣称所有 600 ms 事件都保证无感。
- 实车重复播放、视频高负载、音乐叠加导航、来电/Siri抢占与返回、蓝牙/输出路由变化；记录启动/切歌/提示音/对话延迟，验证视频与触控不随音乐缓冲增长。
- 30–60 分钟播放进度/队列趋势无持续增长；PCM 保真与实际输出音质分别验收。未完成实车及听感复验前不标记最终通过。

参考：https://developer.android.com/reference/android/media/AudioTrack ，https://source.android.com/docs/core/audio/src 。AudioTrack 的实际容量、启动门槛与低延迟能力需按设备/API 检查；Android 输出采样率转换不能由应用配置推定为不存在。
